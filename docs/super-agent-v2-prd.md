# Super Agent v2 PRD

版本：0.2（2026-11-19，America/Los_Angeles）。范围决定：项目负责人。设计与实现：Codex。
状态：**首批原型已在本地验证。独立的 Nori 验收能力、完整 v2、部署和真实产品验收仍待完成。**

本文件是独立的 v2 PRD，不修改现有 Super Agent PRD 的范围、里程碑、完成定义或历史验收。
既有任务执行、续接、原生渠道、记忆和身份边界作为复用基础；v2 的证据与完成状态单独登记。

## 1. 产品目标

Nori 能在日常协作中判断是否值得参与，把长期工作关联到 Linear 和 GitHub，持续提供可核对的
执行与验收证据。默认情况下，Nori 以自己的身份、邮箱和平台账号工作；特定任务可以接受
用户或管理员的委托，包括在有相应授权时以委托人的身份使用其账号。

执行环境继续以 OCI 为主。本期不建设多设备资源池，不引入新的调度器或替换 OpenClaw 原生渠道。
简单问答保持直接处理；不为每条聊天建立工单，不把主动参与等同于获得操作权限。

## 2. 功能范围与设计

### 2.1 独立 Task 与 Linear / GitHub 追踪

- 一个业务 Task 具有跨会话稳定的身份，关联 Linear issue、GitHub issue、原生 task/run、成果和
  acceptance 记录。同一任务的多次执行不产生重复工单；Issue 不是执行器，Session 不是业务任务。
- 优先配置 Linear 官方 GitHub Issues **双向**同步。它负责新工单、状态及受支持字段的传播；
  Nori 的薄适配负责准确关联、发起状态变更、读取两端验证、异常记录和有界恢复。
- Nori 更新任一端后必须检查另一端。同步有延迟时记录 pending，不能说“两边已更新”。网络超时
  可能发生在写入之后，使用持久化 operation ID 和源/目标快照核对，不能盲目重放或新建替代工单。
- 人工改动导致冲突时展示两端事实，保留原始记录，不采用最后写入时间自动覆盖。身份、团队或配对
  改变后旧 receipt 不能在新作用域重放；重启、并发和重复请求必须保持这些约束。
- 细粒度流程以 Linear 状态表达：待办、进行中、待验收、完成、取消等由团队实际配置确定。
  初版适配按 GitHub `open/closed + state_reason` 投影；不声称它表达完整 Linear 流程，
  不把 GitHub Projects 自定义状态当成官方同步能力。GitHub 新状态预览能力需在实际仓库验证后另扩展。
- 已有 GitHub 工单是否导入、哪个 Linear team/project 配对、同步哪些字段，在真实接入时核对。
  官方双向同步会传播内容；私有 Linear 内容不能因此被复制到公开 GitHub 仓库。共享 audience
  在配对前确定，私有讨论保留在不参与同步的讨论区域。
- 工单关闭不自动取消原生执行，重新打开不自动恢复已停任务；执行控制继续使用原生控制和实际结果。
  PR 合并、部署、验证通过、用户接受是不同事实，不能让 PR 自动关闭掩盖“待验收”。

任务追踪接入说明随实现 PR 提交。官方能力依据：
[GitHub Issues Sync](https://linear.app/docs/github)、[Linear GraphQL](https://linear.app/developers/graphql)、
[GitHub Issue API](https://docs.github.com/en/rest/issues/issues#update-an-issue)。

**接入状态（2026-11-19）：** `NORI_LINEAR_TOKEN` 已配置在 OCI 的私有运行环境，并从 OCI 使用保存的密钥
完成 Linear API 认证，确认可读取 Rein Protocol Foundation（REI）团队。这项检查覆盖认证和团队读取。
负责人已配置 GitHub 与 Slack 集成。REI 与目标仓库的 Issues 双向配对、工单写入后两端读回，以及 Nori
任务追踪流程加载凭证，仍需在联调中验证。

### 2.2 Rein Router 内的主动参与判断

目标频道为 Slack **#nori-deployment**。部署时核对实际 account/workspace/channel/agent 组合，用稳定 ID 配置，
不能仅以显示名授予能力。只在该明确配置的范围启用原生 `requireMention: false`。
获准发送联调和验收消息的频道为 Slack **#rein-agent-test**。在该频道核对实际账号、工作区、频道和
Agent 绑定，验证免提及、静默、原生命令和反馈。该测试范围与 `#nori-deployment` 的上线范围分别核定。

处理顺序：原生入口权限 → 低成本规则过滤 → Jev 参与判断 → 既有 Rein Router 模型选择 →
模型执行/按需原生委派 → 判断是否有值得发送的内容 → 正常交付或静默结束。

- Jev 分别判断 **职责相关性** 与 **当前参与是否有帮助**，不把两者合成一个职责阈值。
  例如对 Nori 上一条回复的澄清，即使不属于主要职责，也可能值得回答。
- 未获选的被动消息应正常静默结束，既不启动昂贵回答模型，也不产生“被阻止”错误回复。
  被选中只代表值得进一步处理；后续模型仍可使用原生静默结果，不强迫每次发言。
- `@Nori`、明确回复、原生命令、DM、后台和子任务保留各自原生语义；参与层不能吞掉 stop/status
  等控制命令。反馈、附件、消息动作与线程行为应进行兼容性验证。
- 自己的消息、bot 循环、重复事件和高频噪声有有界控制。Jev 超时、结果无效或资源不足时，被动
  参与保持静默；明确请求保留既有模型与降级路径，不能因分类故障变得不可用。
- Jev 只接收当前授权会话的必要信息；默认不用私有记忆检索来决定是否参与。分类数据不授予工具、
  管理员身份、付费额度或跨 audience 权限。现有模型资格、手动选择和额度限制继续有效。
- 首版允许参与判断和既有模型路由分别调用 Jev；记录实际分类次数、耗时和失败。只有可信跨阶段
  关联接口被证明可用后才合并调用，不用会话级缓存把甲消息的判断错误套到乙消息。

**扩展接口门槛：** 已验证当前 SDK 的 `reply_dispatch` 可对原生普通 Agent 路径在启动 worker 前
静默完成；插件独占 conversation binding 在它之前接管，部分受限 Gateway 路径也不调用该 hook。
这不是通用授权边界。必须保留原生能力并记录真实覆盖范围；完整频道保证不足时保持线上启用待验收，
提出最小的上游“接管前正常静默”接口，不修改只读 vendor 或换掉 Slack adapter。

### 2.3 决策反馈与策略回测

保留决策版本、触发类型、职责/帮助判断、实际模型、耗时和最终是否发言等结构化证据。原始场景如需
回放，使用访问受控的原生记录引用，不把频道全文、用户档案或凭证写入 Git、公共日志或共享技能。

反馈必须绑定具体消息、决策和有权反馈的主体。点赞、点踩、表情或文字可作为候选信号，但单个表情
不是修改生产策略或授予权限的指令。区分“本不应唤醒”“应唤醒但遗漏”“回答错误”。

策略优化流程：采集 → 候选规则/阈值 → 固定场景与反例回测 → 比较误唤醒、漏唤醒、质量和成本 →
版本化推广与回滚。先交付可重放判断与证据；自动反馈摄取、夜间候选生成及生产推广另有独立验收，
不能把分类器测试通过表述为自进化闭环已完成。策略不能自行改写身份、权限、凭证、计费或审批边界。

### 2.4 自身身份与受托身份

| 情形 | 行为主体 | 使用的账号/资源 | 必须记录的事实 |
| --- | --- | --- | --- |
| Nori 自主推进已授权开发/组织工作 | Nori | Nori 自己的账号、邮箱及获授权组织资源 | 任务、实际账号、资源作用域、结果 audience |
| 用户请 Nori 帮忙，但未要求使用用户身份 | Nori | Nori 自己获授权的资源 | 请求者与 Nori 分开记录，不自动冒用请求者 |
| 明确委托以用户身份处理其邮箱/平台账号 | 被委托用户；Nori 是执行代理 | 与该用户验证关联的具体账号 | 委托依据、范围、期限、账号、准许操作、目的地及撤销状态 |

Nori 的自主身份不代表拥有所有组织资源；管理员的请求也不当然授权访问他人的个人邮箱。资源所有者
或有权代表该资源的管理员授予范围，执行前由权威系统或受保护的授权配置核对，聊天身份声明不能替代。

记录 requester、executor（Nori）、represented principal、credential account、resource owner、
cost attribution 和 output audience；可不同，不根据“谁发消息”一项推断。未知费用不记为零。
授权被撤销/过期时停止新增操作；已执行及不确定效果如实保留。延迟结果与重启不能切换主体或扩大范围。

本期先在新增追踪与验收路径落实该契约。已有邮箱/账号适配器逐项审计和验证；不宣称仅修改文档即可
使所有工具支持受托身份，也不为满足 v2 复制用户 workspace 或删除有用记忆。

### 2.5 Nori 独立产品验收（Acceptance）

产品验收回答一个问题：用户现在能否实际获得任务承诺的结果？例如，验证工单双向同步时，Nori 需要
改动测试工单、从另一端读回状态，并将实际结果附在报告里，供验收人接受或退回。

由 Nori 提供独立的验收技能、执行入口和报告。技能放在 `workspace/skills/`，可在 OCI 上用 CLI、
API 或可用的无头浏览器采集证据。核心流程在 Nori 自己的运行环境内完成，禁止依赖 LobeHub 账号、
CLI、API 或托管服务。此前基于 LobeHub 的本地原型只作为历史试验，交付采用 Nori 自己的实现。

- 开始前从任务目标生成可观察的产品验收项，分别声明证据类型、执行环境和验收责任人。
- 每项记录观察、证据、判定及限制；缺少必要证据标为 uncertain/blocked。测试、构建和 CI 是
  工程质量证据，不能替代用户看到/收到的产品结果。
- 产出本地可打开的报告，支持接受/退回、读取反馈和后续轮次。已完成且仍适用的证据复用；只重跑
  受影响项。保留旧轮次、修复与变更来源，不能覆盖原来失败的证据。
- **报告和媒体默认保存在 Nori 的私有运行环境。** 验收人通过授权访问报告和提交反馈。任何外部分享
  或上传都需按受众授权。报告和媒体不得进入 Git 或公共记忆。
- 将报告/回合标识关联 Task、Linear/GitHub；外部工单只能放受众允许访问的报告引用/摘要，不能
  自动复制私有截图。代理判定 pass 与 reviewer 接受分开；没有真人反馈就不能声称已被接受。
- 不需要多设备抽象。环境缺少浏览器、授权或必要账号时准确记录未验收项；本地合成演练不冒充 OCI
  或真实 Slack/Linear 产品验收。

Nori 独立验收的使用说明和验证证据随实现提交。

## 3. 独立验收矩阵

| 验收场景 | 可观察结果 | 所需证据/边界 |
| --- | --- | --- |
| 跨会话任务关联 | 同一 Task 跨会话关联同一对工单及多次真实执行 | 对应 ID、原生 run 和双向链接；无重复创建 |
| 双向状态同步 | 从 Linear 或 GitHub 改状态，另一端最终呈现受支持的对应状态 | 真实两端前后读回；细状态精度明确 |
| 同步故障恢复 | 断网、写后超时、重复/并发、重启不造成盲重放或假同步 | 持久化 receipt、失败/恢复证据 |
| 冲突与访问范围 | 冲突、跨团队/账号/受众和未授权配对被识别 | 不覆盖人工变更，不复制私有内容 |
| 免提及参与 | 指定频道无需 @ 时，相关求助获答，闲聊不触发昂贵 worker/错误消息 | 在 `#rein-agent-test` 实测，记录分类和模型调用。上线前核对生产目标的绑定与行为 |
| 有用的澄清与静默 | 职责外有用澄清可以参与；醒来后仍可静默 | 正反场景，职责与帮助判断分别可见 |
| 原生功能兼容 | 明确呼叫、命令、手动模型、线程/附件、Agent/ACP/插件绑定行为正确 | 实际受影响原生路径；缺接口保留 blocker |
| 故障与噪声控制 | 超时、无效判断、自循环和并发不造成刷屏或额度绕过 | 故障演练、成本/权限兼容性 |
| 回放参与决定 | 能回放有版本的参与决定并识别误唤醒/漏唤醒 | 固定场景及反例结果；不含私密全文 |
| 反馈验证与策略推广 | 真实反馈生成候选，回测后受控推广并可回滚 | 反馈归属、候选/现行比较、推广记录；仍待实现闭环 |
| Nori 自身账号归属 | Nori 自身账号行为不会误归为请求者 | 实际 actor、资源、成本和受众记录 |
| 受托账号授权 | 受托账号只在授权范围/期限内使用，撤销/恢复不串号 | 两账号、过期/撤权和延迟结果验证；不得只测配置字段 |
| 生成本地验收报告 | Nori 能独立从可观察目标生成并执行验收，交付实际本地报告 | 在未安装 LobeHub CLI、未配置其账号的环境完成报告，检查实际操作和证据覆盖 |
| 退回与再次验收 | 缺证据不会通过；用户退回可形成下一轮并保留历史 | 原始证据、反馈读回、不可变轮次 |
| 报告默认保存在本地 | Nori 私有保存报告、证据和反馈，授权验收人可打开报告 | 禁用第三方验收服务访问后演练完整流程，核对无自动上传及报告的访问权限 |
| 工单关联与验收状态 | 验收结果与工单关联，待验收/已通过/已接受区别可见 | 任务关联与真实 reviewer 反馈；无自动假批准 |

# Super Agent v2.1 PRD：从日常对话到 Linear 任务

日期：2026-11-19。状态：需求提案，待实现与真实验收。

## 用户应当体验到什么

在 Slack 里对 Nori 说「把周报导出加上日期列，周五前给我一个样例」，即使没说“建单”，Nori 也能识别出交付物和后续跟进的需要。在已授权的项目和公开范围内，它找到或创建一张 Linear 工单，在原线程返回工单链接，并按这张工单推进。隔天换一个线程说「继续昨天的周报日期列，先给我看样例」，Nori 能从原单接着做。验收人退回样例后，修改、复验和最终反馈仍落在同一单上。

[Super Agent v2](super-agent-v2-prd.md) 已定义稳定的业务任务、双向状态同步、原生执行和验收关联。[现有建单入口](../reference/task-pairing.md) 从预先配置好标题和正文的任务创建 GitHub 源工单。v2.1 新增从普通对话识别任务、在授权范围内由 Nori 拟定工单、优先写入 Linear，以及从同一张工单恢复下一步工作的流程。

## 什么时候建单

参与群聊和创建工单是两个独立决定。Nori 可以回复问题而不建单。进入任务判断时，结合当前消息、获准读取的上下文以及已有任务，按以下规则处理。

| 对话里的信号 | Nori 的行为 |
| --- | --- |
| 一次性问答、闲聊、状态查询，例如「周报在哪里下载？」 | 直接回答、查询已有工单或保持静默，不产生新工单。 |
| 讨论可能性，例如「以后也许可以加日期列」，尚无人交办 | 作为讨论处理。若后续有人明确交办，再判断是否立项。 |
| 用户明确要求记录一个具体事项，或明确把工作交给 Nori，且有可辨识的交付目标，需要后续执行、等待、协作或验收 | 先查重。目标、权限和受众已明确时自动建单或复用，返回结果；无需用户再说一遍“请建单”或逐字审批标题。 |
| 对既有工作补材料、改约束、反馈失败或催进度 | 定位原单，把新信息用于下一步执行或状态答复。只有目标可以独立交付和验收时，才考虑另建关联工单。 |
| 无法判断指的是哪个任务，或缺少会改变执行方向的关键信息 | 在原线程提出一个能消除歧义的问题。能从授权上下文或现有工单确定的字段由 Nori 补齐。 |

公开范围是建单条件。REI 与公开 GitHub 仓库双向同步，因此写入 REI 也可能公开标题、正文和同步评论。Nori 在检索、写入和跨会话续办前核对请求者、账号、任务作用域和输出受众。已有授权覆盖时自动处理。内容涉及私有对话或授权不明时，保留私有草稿，询问可以公开的具体表述或使用已有的获准私有去向。工单创建成功只说明任务已登记，具体执行仍遵守任务本身的权限。

## 如何找到原单并防止重复

1. 优先解析显式 Linear 编号、链接、GitHub 对应工单和已有线程绑定，核对团队、仓库、访问范围及业务任务身份。用户给的是 GitHub 链接时，沿已验证的双向关联找到 Linear 原单。
2. 没有显式引用时，在当前主体有权访问的任务范围内，按交付目标、对象、项目、已有成果和验收条件查找。只有一个明确匹配时复用，并回告链接。标题相似、人员相同或处在同一个频道，只能用来找候选。多个候选无法区分时，在授权受众内询问用户选择。
3. 已关闭工单收到追问时先报告原结果。原交付物被退回时沿原单复验，需重新打开时遵守工单权限。目标已经变化且可独立验收时，另建关联任务并说明原因。
4. 把 Slack 重投、并发消息、跨线程引用和重启当作正常情况。外部写入前持久化稳定的任务身份和建单意图，并协调指向同一任务的并发创建。若已有写入可能成功，先恢复记录并读回；无法确定时保留待核对状态。验收要求是同一任务只出现一张 Linear 单和一个对应的 GitHub Issue。

## Linear 首建与跨会话推进

- **登记。** 确认没有可复用工单后，由 Nori 在获准的 Linear 团队创建源工单。写下目标、可观察的完成条件、已知约束和下一步。负责人、期限等只填写已有依据的内容。记录实际 Linear 编号并在原线程返回链接。已登记而尚未开始执行时，如实说明。
- **同步。** 由 Linear 官方集成生成 GitHub Issue。核对目标仓库、两端编号和实际关联后，才报告双端已同步。同步慢、网络超时或受限时，保留原 Linear 工单，报告当前状态并有界重查；恢复过程中不得在 GitHub 手工补建副本。
- **执行与阻塞。** 每次续办先读取原单的最新状态、已验证成果、阻塞和下一步，关联新的原生执行记录。完成一个里程碑时更新原单的进展和相应证据。遇到阻塞时写清缺什么、需要谁处理、什么条件下能继续。收到解除阻塞的消息后沿原单继续。并发或人工编辑出现冲突时保留双方事实，避免旧执行覆盖新进展。
- **验收。** 交付候选成果后转为待验收，关联 Nori 私有验收报告，仅向公开工单写受众允许的摘要。验收人退回时在原单记录原因、修改与下一轮；实际接受后记录反馈和完成状态。工单显示进展，OpenClaw 负责执行，验收记录保存证据与真实决定。[任务与执行关联](../reference/task-links.md)
- **恢复。** 换线程、换会话或进程重启后，用稳定任务身份恢复同一 Linear 编号、GitHub 对应关系、最近执行及验收轮次。新会话可见范围不足时，在获准的上下文中继续，回复中不得泄露其他受众的任务或成果。

## Slack 真实验收

在获准的 `#rein-agent-test` 用真实 Slack test account 和 admin account 发起对话。开始前核对两个账号的实际身份、后端角色、目标团队和仓库；管理员正例需要真实有效的管理员权限。使用可公开、带测试标识的新案例。通过正常的 Slack 消息入口触发，记录消息事件、实际 Linear 编号、GitHub 对应关系、原生执行与验收轮次。私有证据留在受控位置。

| 场景 | 操作与通过条件 |
| --- | --- |
| 问答和讨论 | test account 先问如何下载，再提出无承诺的改进设想。Nori 可以回答或静默；检查这两条消息均未产生工单。 |
| 不说“建单”的明确交办 | 有权的账号在普通对话中明确交付目标。无需预配该任务的标题和正文，Nori 自动先创建一张 Linear 源单并回复其链接，随后读回官方同步的 GitHub Issue。用两端创建证据核对方向与数量。 |
| 复用与消歧 | 同一请求被重投或在另一线程被重新表述，只关联原单。再准备两个目标相近但可独立验收的任务，发送模糊追问；Nori 询问指向哪一个，得到答案后只更新选定工单。 |
| 写后超时与重启 | 通过真实 Slack 交办，在隔离的验收实例中让成功的 Linear 写入丢失响应，或延迟观察 GitHub 对应单。重启后重送请求，从已有意图找回原单。两端各只有一单，回复能区分待同步和已同步。 |
| 跨会话推进 | test account 发起任务，Nori 执行并记录一个真实阻塞。另起会话，由有权的 admin account 提供缺失信息，Nori 读回原单、解除阻塞、继续执行。查看同一 Linear 单能还原两次执行的进展与下一步。 |
| 退回与接受 | Nori 把可交付成果送审。指定的真实验收人在 Slack 退回一项，修复后再次验收并接受。原单保留两轮结果，最终状态有实际反馈，GitHub 对应单反映支持的状态。 |
| 公开与身份边界 | 用无敏感内容的模拟私密材料提出交办，或让无权测试账号请求更新另一受众的任务。Nori 保留私有草稿、追问或拒绝越权操作；检查公开两端没有相关内容。获准账号提供可公开摘要后，只按该摘要登记一次。 |

交付时逐项报告观察结果、对应证据和未覆盖条件。对输入重复、超时和重启可使用受控故障注入，并注明注入位置。真实 Slack 触发、两端实际工单和真人验收决定分别保留可核对的记录。

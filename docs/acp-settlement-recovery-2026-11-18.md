## Root cause and supported boundary

At pinned OpenClaw `4a11f89e840b2bb3eedcad2820ab25b8520905b6`, ACP Task `succeeded` is
written before the manager finishes cleanup. The earlier controller depended on a later parent
status/review call to obtain and persist `agent.wait` evidence. A lost parent turn or process restart
before that write leaves a terminal Task without a saved execution-settlement receipt.

A public interface previously unused by this adapter provides a stronger signal:
`api.runtime.events.onAgentEvent`. `src/agents/command/acp-execution.ts` awaits manager.runTurn,
including cleanup, then emits lifecycle completion through `attempt-execution.ts`. The producer
explicitly sets `data.executionSettled=true`. Its exact run ID can be checked against the current
owner-bound native Task and accepted Flow attempt before saving a small receipt.

The fix captures that native event independently of parent-model success. It must not perform
semantic review, mark a Flow complete, reset budgets, infer delivery, or trust a chat claim. A
failure/cancellation event establishes execution end only; it cannot certify a successful result.
The existing parent review remains mandatory. Tests and real acceptance are recorded below.

## Historical and crash limitations

The historical run `3a180afa…` has no saved receipt. Although its transcript is written after
cleanup, the native writer converts terminalOutcome into stopReason and does not persist exact
runId/terminalOutcome. The public session messages API does not restore that provenance. Plain
text, timestamps, session idle and Task succeeded do not safely prove this old run's settlement.
The original run must remain unresolved; it is not retried, reset or rewritten as successful.

Public event listeners return void and the host does not await their asynchronous writes. Pending
write draining can protect orderly shutdown, but abrupt termination before persistence remains
unknown. Strict crash-atomic recovery requires an upstream owner-fenced durable exact-run receipt
committed before notification, exposed through the owner-bound Task API. This patch does not alter
read-only vendor code or claim that stronger upstream guarantee.

## Parent/observer concurrency follow-up

A deterministic test exposed a narrower race: a parent holding revision N can lose its CAS
when passive receipt persistence advances the Flow to N+1. Evidence was safe, but the parent
received a revision conflict. The follow-up permits at most one fully reauthorized recomputation
for explicit-flow status/review only, when the sole intervening change is that exact attempt's
native lifecycle receipt. Owner/scope/stop/report/budget changes, altered arguments, lost authority,
session resets, changed native Task fingerprints and a second conflict still fail. All-flow status,
spawn/delegate, stop and change actions are never replayed. No stale review state bypasses CAS.
